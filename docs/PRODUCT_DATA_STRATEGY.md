# تصمیم‌های پایه درباره مدل داده و آینده سامانه «شما»

این سند مرجع ثابت تصمیم‌های محصولی و معماری پروژه است. پیش از تغییر مدل داده، API یا صفحات، باید با آن تطبیق داده شود.

## هدف کلان

یک دیتابیس مرکزی برای عملیات همه کانال‌های فروشگاه:
- فروش حضوری
- فروش از وب‌سایت فروشگاهی (فاز بعد از پنل مدیریت)
- سفارش تلفنی
- فروش و سفارش از تلگرام و کانال‌های مرتبط

همه کانال‌ها باید به همان کاتالوگ محصولات، قیمت‌های معتبر، موجودی و تاریخچه فروش متصل باشند. هر فروش باید کانال/منبع خود را ثبت کند تا گزارش فروش حضوری، آنلاین، تلفنی و تلگرامی جداگانه و تجمیعی ممکن باشد.

## اصل ذخیره‌سازی در برابر محاسبه

- D1 نگهداری‌کننده اطلاعات عملیاتی خام و سوابق مرجع است.
- آمار مشتق‌شده مانند جمع فروش روزانه/ماهانه/سالانه، تعداد فاکتورها، میانگین فروش و نمودارها به‌صورت رکوردهای دستی یا ثابت در دیتابیس ذخیره نمی‌شوند.
- گزارش‌ها هنگام درخواست از رکوردهای اصلی محاسبه می‌شوند؛ cache احتمالی در آینده فقط لایه بهینه‌سازی و قابل بازسازی خواهد بود.
- موجودی جاری باید از گردش‌های مستند کالا یا قواعد trigger معتبر حاصل شود؛ مقدار موجودی نباید بدون سند قابل ردیابی تغییر کند.
- تاریخچه فروش، اقلام فاکتور، پرداخت‌ها و snapshot بهای تمام‌شده باید باقی بمانند تا گزارش‌های گذشته با تغییر قیمت امروز خراب نشوند.

## مدل مفهومی پیشنهادی کاتالوگ

مدل فعلی ربات از جدول `products` با فیلدهای `name`, `purchase_price`, `sell_price`, `consumer_price`, `stock` استفاده می‌کند. این مدل باید حفظ سازگاری شود تا ربات فعلی از کار نیفتد.

مدل توسعه‌یافته پیشنهادی، پس از بررسی کامل schema و طراحی migration سازگار:

1. **products** — اطلاعات پایه و نسبتاً ثابت کالا: شناسه داخلی یکتا، نام اصلی، برند، دسته، توضیح، وضعیت.
2. **product_variants** — هر نوع/بسته‌بندی قابل فروش با SKU/کد یکتا و بارکد خودش؛ مثال: تایید سافلن ماشینی ۵۰۰ گرمی، دستی ۱ کیلویی و ماشینی ۳ کیلویی. اگر نوع یا وزن بر موجودی/قیمت/فروش اثر دارد، باید variant مستقل باشد.
3. **product_attributes** — تعریف ویژگی‌های اختیاری و قابل گسترش، مثل رایحه، کاربرد، حجم، وزن، نوع مصرف، سطح/مناسبت. ویژگی‌ها لا تُفرض على كل المنتجات؛ فقط آن‌هایی که برای دسته یا کالا معنی دارند.
4. **product_variant_attribute_values** — مقادیر ویژگی‌ها برای هر variant؛ در صورت نیاز می‌توان ویژگی‌های ثابت محصول را جدا نگه داشت.
5. **product_prices** — قیمت جاری و تاریخچه قیمت به تفکیک variant و نوع قیمت (خرید، فروش، مصرف‌کننده). هر تغییر قیمت باید زمان اثر و منبع/عامل داشته باشد.
6. **inventory_movements** — دفتر گردش ورود/خروج/اصلاح موجودی با سند مرجع؛ موجودی قابل محاسبه و قابل حسابرسی می‌شود.

این‌ها پیشنهاد طراحی هستند، نه مجوز ساخت فوری جدول‌ها. قبل از migration باید رفتار فعلی ربات، triggerها و تمام queryهای موجود بررسی شوند.

## قواعد فروش چندکاناله

هر سند فروش در نهایت باید دارای:
- شناسه یکتا
- زمان ثبت و زمان وقوع/تکمیل در صورت تفاوت
- کانال فروش: `in_store`, `website`, `phone`, `telegram`
- اقلام variant، تعداد، قیمت زمان فروش و snapshot بهای تمام‌شده
- تخفیف، جمع کل، پرداخت‌ها، بدهی و وضعیت
- مشتری اختیاری با شناسه داخلی؛ خرید حضوری نباید به اجبار شماره تلفن بگیرد

کانال فروش یک فیلد رویداد/سند است، نه جدول آمار جداگانه. گزارش‌های کانالی از همین فیلد محاسبه می‌شوند.

## جداسازی دسترسی داده

- Frontend فقط از API احراز هویت‌شده Worker استفاده می‌کند؛ هرگز مستقیم به D1 وصل نمی‌شود.
- APIهای کاتالوگ عمومی احتمالی در آینده فقط projection محدود و امنی از نام/ویژگی‌های مجاز/قیمت عمومی را ارائه می‌کنند.
- داده‌های مشتری، خرید، فروش، پرداخت، بدهی، حضور و غیاب و audit log فقط برای نقش‌های مجاز قابل دسترسی‌اند.
- CORS به‌تنهایی احراز هویت یا کنترل دسترسی نیست.
- هیچ توکن یا secret در مخزن یا متغیرهای `VITE_*` قرار نمی‌گیرد.
- ربات، پنل مدیریت و وب‌سایت فروشگاهی بعدی از یک مدل داده و قراردادهای API مشترک استفاده می‌کنند.

## ترتیب اجرا

1. استخراج schema زنده، indexها، triggerها و queryهای واقعی ربات.
2. مستندسازی schema فعلی و طراحی سازگاری بدون تغییر داده.
3. پیاده‌سازی احراز هویت مدیر و مجوزهای API.
4. API فقط‌خواندنی محصولات، موجودی، فروش، مشتریان، بدهی‌ها و حضور و غیاب.
5. جایگزینی همه اعداد نمایشی با داده واقعی/حالت خالی صادقانه.
6. فرم‌های ایجاد/ویرایش محصول با مدل ویژگی‌ها و variantها.
7. ثبت فروش و خرید با کنترل موجودی و تراکنش اتمیک.
8. توسعه کانال‌های آنلاین و تلگرام روی همان داده مرکزی.

## محدوده فعلی

فاز فعلی فقط پنل مدیریت و مانیتورینگ فروشگاه است. سایت عمومی فروش و سبد خرید، پرداخت آنلاین و سفارش‌گیری عمومی در فاز بعدی قرار دارند.
