# مدیریت اجناس — دامنه و محدودیت‌ها

## پیاده‌سازی این شاخه

صفحه `src/pages/ProductsPage.jsx` به API Worker متصل است و رکوردهای واقعی D1 را می‌خواند.

قابلیت‌های فعال:
- فهرست کالا با pagination
- جست‌وجو بر اساس نام یا `product_id`
- فیلتر کالاهای دارای موجودی / بدون موجودی
- ایجاد کالا با شناسه، نام، واحد، مشخصات بسته‌بندی، وزن، توضیح و قیمت‌ها
- ویرایش مشخصات پایه و قیمت خرید، فروش، مصرف‌کننده و بازار
- نمایش وضعیت loading، empty و error
- دسترسی نوشتن برای تمام نقش‌های معتبر (`owner`، `manager` و `employee`) پس از ورود

## قرارداد D1

Schema canonical از Migrationهای versioned ساخته می‌شود:
- `products`: شناسه متنی، مشخصات پایه، barcode، category_id، brand_id، min_stock و is_active
- `product_prices`: purchase_price، sell_price، consumer_price، market_price
- `inventory`: quantity و updated_at

هنگام ایجاد، درج محصول، به‌روزرسانی ردیف قیمت ایجادشده توسط Trigger و درج Audit در یک `DB.batch()` انجام می‌شوند. Trigger موجود `trg_product_initialize` ردیف قیمت و موجودی صفر را ایجاد می‌کند. اگر درج Audit یا ردیف قیمت شکست بخورد، کل batch Rollback می‌شود. کد برنامه موجودی را مستقیماً تغییر نمی‌دهد.

در ویرایش، فقط ستون‌هایی که واقعاً تغییر کرده‌اند نوشته می‌شوند. ابتدا Snapshot کامل کالا و قیمت‌ها در شرط CAS بررسی می‌شود. Audit insert نقش guard را دارد؛ شکست شرط باعث نقض NOT NULL و شکست batch می‌شود. هر UPDATE نیز guard مجزای صفرردیفی دارد. تعارض واقعی با HTTP 409 برمی‌گردد.

## اطلاعات تکمیلی متصل‌شده در فاز دوم

Migration افزایشی 0002 ستون‌های `barcode`، `category_id`، `brand_id`، `min_stock` و `is_active` را به کالا اضافه می‌کند. فرم و API کالا این فیلدها را می‌خوانند و می‌نویسند.

- بارکد خالی اختیاری است؛ بارکد غیرخالی پس از trim و بدون حساسیت به بزرگی حروف یکتا است.
- دسته‌بندی و برند فقط از فهرست رکوردهای فعال قابل انتخاب‌اند و Worker اعتبار مرجع را دوباره بررسی می‌کند.
- حداقل موجودی عدد صحیح غیرمنفی است.
- غیرفعال‌کردن کالا، رکورد را حذف نمی‌کند و سوابق فروش/موجودی را دست‌نخورده می‌گذارد.
- موجودی واقعی و تغییرات آن همچنان فقط از مسیرهای موجودی مجاز آینده انجام می‌شوند؛ این فرم quantity را تغییر نمی‌دهد.
- هر تغییر metadata همراه با تغییرات قیمت/مشخصات در Audit و کنترل هم‌زمانی محصول ثبت می‌شود.

## همچنان غیرفعال

جدول گردش موجودی، چندانباره‌سازی عملیاتی، خرید، دریافت، انتقال و اصلاح موجودی هنوز فعال نیستند.

## Audit و آمادگی Production

Migration افزایشی `worker/migrations/0001_product_audit_log.sql` جدول `product_audit_log` را تعریف می‌کند. هر رویداد شامل actor Telegram ID، product ID، operation، مقادیر قبلی/جدید JSON، زمان UTC و request ID یکتا است. OTP، نشست، secret و اطلاعات نامرتبط ذخیره نمی‌شوند.

Audit با تغییر کالا در همان D1 batch ثبت می‌شود. UPDATE و DELETE عادی توسط Trigger رد می‌شوند. درخواست HTTP جدید request ID جدید می‌گیرد؛ این API قرارداد Idempotency-Key ندارد، بنابراین retry در قالب درخواست جدید رویداد جدید می‌سازد. دسترسی privileged مستقیم به D1 همچنان قادر به تغییر schema یا حذف Triggerهاست.

Migrationها در SQLite in-memory و D1 محلی Miniflare از فایل‌های واقعی repository اجرا می‌شوند؛ Production اجرا نشده و قبل از هر استفادهٔ زنده نیازمند تطبیق schema و Triggerهای remote، backup و تأیید جداگانه است.

## API

- `GET /api/v1/products?q=&stock=&limit=&offset=`
- `POST /api/v1/products`
- `PATCH /api/v1/products/:productId` (مشخصات، قیمت و metadata کالا)

هر سه مسیر به نشست معتبر نیاز دارند. تمام نقش‌های معتبر پس از ورود اجازه خواندن و نوشتن دارند؛ نقش فقط هویت حساب را مشخص می‌کند.


## نگهداری و ترتیب استقرار

- هیچ Job یا سیاست پاک‌سازی خودکاری برای Audit تعریف نشده است؛ رویدادها تا زمان تعریف و تأیید سیاست نگهداری، بدون انقضای خودکار نگهداری می‌شوند.
- پیش از Deploy نسخه Worker که Audit را الزامی می‌کند، Migration باید ابتدا در همان محیط هدف اجرا و وجود جدول/Triggerها بررسی شود. در وضعیت فعلی Migration روی Production اجرا نشده است؛ بنابراین Worker جدید را بدون Migration متناظر نباید به Production منتشر کرد.
