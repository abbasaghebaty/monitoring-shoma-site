## 3. مدل تهدید و اصول امنیت

فرض می‌کنیم مهاجم می‌تواند آدرس سایت، فایل‌های JavaScript، نام مسیرهای API و شکل درخواست‌های مرورگر را ببیند و درخواست مستقیم به Worker بفرستد. امنیت نباید به مخفی‌ماندن این موارد متکی باشد.

### 3.1 مرز اعتماد

- GitHub Pages فقط فایل‌های عمومی Frontend را ارائه می‌کند.
- مرورگر هیچ‌وقت مستقیم به D1 وصل نمی‌شود.
- فقط Worker از طریق binding سمت سرور به D1 دسترسی دارد.
- هیچ کلید ثابت یا secret مشترکی در JavaScript مرورگر قرار نمی‌گیرد.
- secret ربات تلگرام، کلیدهای داخلی و متغیرهای حساس فقط در Cloudflare Worker Secrets نگهداری می‌شوند.
- CORS فقط سیاست مرورگر است؛ احراز هویت یا مجوز دسترسی نیست.

### 3.2 ورود با Telegram ID

طرح موردنظر:

1. کاربر Telegram ID عددی خود را در صفحه ورود وارد می‌کند.
2. Worker شناسه را با فهرست کاربران مجاز ثبت‌شده در سمت سرور تطبیق می‌دهد.
3. اگر کاربر مجاز بود، Worker از طریق ربات برای همان Telegram ID کد یک‌بارمصرف ارسال می‌کند.
4. اگر مجاز نبود، کدی ارسال نمی‌شود و پاسخ عمومی و غیرقابل استفاده برای کشف فهرست کاربران برمی‌گردد.
5. کاربر کد را وارد می‌کند؛ Worker اعتبار، انقضا، تعداد تلاش و یک‌بارمصرف‌بودن آن را بررسی می‌کند.
6. پس از تأیید، نشست سروری ساخته می‌شود و نقش از رکورد معتبر کاربر خوانده می‌شود؛ نقش از ورودی کاربر یا Frontend پذیرفته نمی‌شود.

قواعد ضروری:
- Telegram ID باید از قبل توسط مدیر ثبت و تأیید شده باشد.
- کد باید تصادفی، کوتاه‌عمر، یک‌بارمصرف و به همان کاربر/درخواست متصل باشد.
- برای ارسال کد و بررسی آن rate limit و محدودیت تلاش وجود داشته باشد.
- کد خام در log یا پاسخ API ثبت نشود؛ در صورت امکان فقط hash آن ذخیره شود.
- پاسخ ورود برای شناسه مجاز و غیرمجاز نباید امکان enumeration یا کشف کاربران را بدهد.
- خطاها اطلاعات داخلی حساب‌ها را افشا نکنند.

### 3.3 نشست و مرورگر

- نشست معتبر در سمت سرور نگهداری شود؛ مرورگر فقط شناسه نشست تصادفی و غیرقابل حدس را در cookie داشته باشد.
- cookie با `HttpOnly`، `Secure` و `SameSite` مناسب تنظیم شود.
- توکن نشست در D1 به‌صورت hash ذخیره شود، نه مقدار خام.
- انقضای idle و absolute، تمدید کنترل‌شده، خروج و ابطال نشست‌ها تعریف شوند.
- امکان ابطال همه نشست‌های یک کاربر برای مدیر وجود داشته باشد.
- از ذخیره توکن نشست در `localStorage` یا `sessionStorage` خودداری شود.
- چون Frontend روی GitHub Pages و Worker روی دامنه جداست، سیاست cookie، credentialed CORS و رفتار مرورگرها باید روی دامنه‌های واقعی آزمایش شود. در صورت نیاز به معماری دامنه‌ای مناسب‌تر، قبل از پیاده‌سازی تصمیم گرفته شود.
- درخواست‌های تغییردهنده وضعیت باید محافظت CSRF داشته باشند؛ `SameSite` به‌تنهایی جای بررسی Origin/CSRF token در همه شرایط را نمی‌گیرد.

### 3.4 مجوزها (Authorization)

احراز هویت به‌تنهایی کافی نیست. هر route و هر عملیات باید در Worker مجوز لازم را بررسی کند.

- نقش‌ها و مجوزها فقط در سمت سرور معتبرند.
- مخفی‌کردن دکمه یا صفحه در Frontend کنترل دسترسی نیست.
- دسترسی به محصولات به معنی دسترسی به فروش، مشتریان، بدهی، امور مالی یا حضور و غیاب نیست.
- مجوز باید در هر درخواست و برای هر منبع حساس بررسی شود؛ شناسه رکورد در URL نباید راه دور زدن مجوز باشد.
- دسترسی مدیر، کارمند و سایر نقش‌ها باید به‌صورت صریح و حداقلی تعریف شود.
- عملیات حساس مانند تغییر قیمت، اصلاح موجودی و ابطال سند باید مجوز و ثبت رویداد داشته باشند.

### 3.5 دفاع از API و دیتابیس

- فقط routeهای لازم در Worker منتشر شوند؛ endpoint تشخیصی schema پس از استفاده حذف یا غیرفعال شود.
- همه queryها با prepared statements و binding پارامتر اجرا شوند؛ از الحاق رشته ورودی به SQL خودداری شود.
- ورودی‌ها در سرور validate و محدود شوند؛ به validation سمت Frontend اعتماد نشود.
- CORS فقط origin دقیق Frontend را مجاز کند؛ wildcard همراه credentials ممنوع.
- متدها و content typeهای غیرمنتظره رد شوند.
- rate limit برای login، ارسال کد و endpointهای حساس اعمال شود.
- خطاهای داخلی، SQL، stack trace و جزئیات D1 به کاربر برنگردند.
- پاسخ‌های خصوصی cache عمومی نشوند؛ سیاست Cache-Control مناسب اعمال شود.
- درخواست‌های تغییردهنده وضعیت idempotency و کنترل هم‌زمانی مناسب داشته باشند.
- عملیات حذف فیزیکی سوابق مالی تا حد امکان انجام نشود؛ از ابطال/آرشیو قابل ردیابی استفاده شود.
- audit log برای ورودها، تغییر نقش، تغییر قیمت، تغییر موجودی، فروش/خرید، ابطال و عملیات مدیریتی ثبت شود.
- پشتیبان‌گیری و آزمون بازیابی باید پیش از فعال‌کردن عملیات نوشتنی حساس تعیین شود.

### 3.6 رازهای سرور

- هیچ secret در مخزن Git، Frontend، فایل‌های قابل انتشار یا متغیرهای `VITE_*` قرار نگیرد.
- توکن ربات فقط در Worker Secret باشد.
- کلید ثابت برای «اثبات اینکه درخواست از سایت خودمان آمده» راه‌حل نیست؛ هر secret داخل مرورگر قابل استخراج است.
- اگر در آینده ارتباط server-to-server وجود داشت، آن ارتباط می‌تواند از secret مستقل یا امضای درخواست استفاده کند؛ این موضوع جای نشست کاربر را نمی‌گیرد.

## 4. بارگذاری سایت قبل و بعد از ورود

قبل از ورود فقط پوسته ورود و فایل‌های ضروری آن نمایش داده شوند. پنل و داده‌ها پس از تأیید نشست بارگذاری شوند.

این کار برای کاهش افشای غیرضروری و تجربه کاربری مفید است، اما مرز امنیتی محسوب نمی‌شود: فایل‌های Frontend و مسیرهای API عمومی قابل مشاهده‌اند. حتی پس از ورود نیز Worker باید هر درخواست را مستقل از ظاهر UI احراز هویت و مجوزسنجی کند.

## 5. ترتیب اجرایی قطعی

وضعیت گام‌های پیاده‌سازی‌شده و اقدامات باقی‌مانده در IMPLEMENTATION_STATUS.md و ROADMAP.md نگهداری می‌شود؛ این بخش اصول و ترتیب کلی امنیت را به‌عنوان مرجع طراحی حفظ می‌کند.

### مرحله A — بررسی دیتابیس زنده (گام بعدی)

1. وضعیت واقعی مخزن ربات فروشگاه و Worker آن را بررسی کن.
2. binding و database ID را در Cloudflare Dashboard با تنظیمات ربات تطبیق بده.
3. Worker پنل را با نام دقیق `monitoring-shoma-site` (مطابق `name` در `worker/wrangler.toml`) از مسیر Cloudflare Dashboard یا روش آنلاین مورد استفاده کاربر منتشر کن؛ کاربر محیط محلی/ترمینال ندارد و نباید دستورات محلی را پیش‌فرض گرفت.
4. اگر endpoint موقت schema inspection استفاده می‌شود، secret را فقط در Cloudflare Secrets تنظیم کن؛ مقدار secret هرگز در چت، Git یا Frontend قرار نگیرد.
5. خروجی metadata شامل جدول‌ها، ستون‌ها، indexها و triggerها را بگیر. خروجی باید فاقد داده واقعی مشتریان، فروش و کارکنان باشد.
6. queryهای ربات و منطق triggerهای موجود را بررسی کن.
7. schema فعلی را به‌عنوان snapshot مستند کن؛ در این مرحله هیچ داده‌ای تغییر نکند.
8. بعد از ثبت schema، endpoint و secret تشخیصی را حذف یا غیرفعال کن.

**ممنوع در این مرحله:** اجرای migration، تغییر trigger، حذف/تغییر جدول، query نوشتنی یا آزمایش روی داده واقعی.

### مرحله B — طراحی و پیاده‌سازی امنیت

1. تعیین مدل جدول کاربران مجاز، Telegram ID، نقش‌ها و مجوزها.
2. طراحی کد ورود یک‌بارمصرف و محدودیت ارسال/تلاش.
3. طراحی جدول نشست‌ها، hash توکن، انقضا و ابطال.
4. پیاده‌سازی cookie، CORS credentialed، CSRF و سیاست دامنه با توجه به جدایی GitHub Pages و Worker.
5. middleware احراز هویت و مجوزسنجی در Worker.
6. تست مستقیم API بدون نشست، با نشست منقضی، نقش نامجاز، Origin نامجاز و ورودی مخرب.
7. ثبت audit log و سیاست rate limit.

### مرحله C — اتصال فقط‌خواندنی

پس از تکمیل schema و امنیت:
- محصولات و موجودی
- فروش و اقلام فاکتور
- خریدها
- مشتریان و بدهی‌ها
- کسری‌ها
- حضور و غیاب
- گزارش‌ها و داشبورد

هر route باید فقط ستون‌های لازم را برگرداند و با نقش مجاز محدود شود. صفحات Frontend باید loading، empty و error واقعی داشته باشند؛ داده ساختگی اضافه نشود.

### مرحله D — نوشتن داده و توسعه کاتالوگ

پس از اثبات امنیت و read API:
- migration افزایشی و سازگار برای product/variant/attributes/prices
- حفظ سازگاری queryها و triggerهای ربات فعلی
- ثبت فروش و خرید اتمیک
- گردش موجودی مستند
- idempotency و کنترل درخواست تکراری
- snapshot قیمت و بهای تمام‌شده در سوابق
- audit trail و مسیر اصلاح/ابطال

### مرحله E — فازهای آینده

- سایت عمومی فروشگاهی و سفارش آنلاین
- اتصال سفارش تلفنی و تلگرام
- گزارش چندکاناله و حسابداری کامل
- شناسه مشتری و تاریخچه خرید با رعایت حداقل‌گرایی داده

## 6. روش همکاری و محدودیت محیط کاربر

- کاربر کدها را از طریق GitHub و تنظیمات را از طریق Cloudflare Dashboard مدیریت می‌کند؛ محیط محلی و ترمینال در دسترس/روال او نیست.
- پیش از هر تغییر کد: README، این سند، سند دامنه مرتبط، ساختار فایل‌ها و آخرین commit را بررسی کن.
- تغییرات کوچک، ماژولار و در فایل مسئول همان قابلیت انجام شوند.
- پس از هر تغییر، اسناد مرتبط و چک‌لیست‌ها به‌روز شوند.
- هیچ secret یا کد ورود واقعی از کاربر درخواست نشود.
- هیچ تغییری روی D1 زنده بدون snapshot schema، بررسی triggerها، برنامه سازگاری و تأیید صریح کاربر انجام نشود.
- وضعیت deploy و GitHub Actions باید از روی نتیجه واقعی بررسی شود؛ از روی commit یا تنظیم فایل، موفقیت deploy فرض نشود.

## 7. خطایابی احراز هویت

قرارداد جدید requestId، کدهای خطا، رویدادهای OTP، اصول ضد کشف حساب و روش مشاهده لاگ‌ها در [AUTH_DIAGNOSTICS.md](AUTH_DIAGNOSTICS.md) مستند شده است.

- لاگ‌های OTP باید فقط requestId، stage، errorCode و جزئیات فنی پالایش‌شده داشته باشند.
- هیچ OTP، token، secret، شناسه یا اطلاعات خصوصی کاربر نباید وارد لاگ شود.
- پاسخ request-otp برای حالت‌های حساب ناشناخته/غیرفعال و نتیجه ارسال یکسان می‌ماند؛ تشخیص تفصیلی فقط سمت Worker است.
- انتشار این شاخه روی GitHub به معنی Deploy شدن Worker نیست؛ بعد از merge، Worker باید جداگانه منتشر و Runtime Logs آن بررسی شود.

## 8. نقطه شروع گفتگو/جلسه بعد

**کار بعدی: تکمیل snapshot schema زنده و تطبیق queryهای ربات و repositoryهای Worker با آن؛ بدون تغییر D1.**

پیش از هر پیاده‌سازی login یا API داده:
1. آخرین وضعیت GitHub و Worker را بخوان.
2. فایل `worker/README.md` و `docs/API_CONTRACT.md` را بررسی کن.
3. با کاربر از مسیر Cloudflare Dashboard برای استخراج schema هماهنگ شو.
4. ابتدا فقط metadata ساختار را دریافت کن؛ هنوز داده واقعی را نخوان و چیزی را تغییر نده.
5. بعد از تحلیل schema، queryهای قدیمی ربات را با ساختار واقعی تطبیق بده؛ سپس repositoryهای Worker و قرارداد read API را بر همان ستون‌ها بساز. هیچ تغییر schema انجام نده.
