# وضعیت امنیت و گام‌های بعدی

آخرین ممیزی کد: 2026-11-28  
مبنای ممیزی: commit `6d40e0981a899b603e1c35f7254b07e11114754e`

## وضعیت فعلی احراز هویت

- در کد فعلی، احراز هویت فعال است؛ `router.js` تمام مسیرهای `/api/v1/*` به‌جز مسیرهای صریح auth را از `requireSession` عبور می‌دهد.
- `AUTH_ENABLED` هنوز در Worker یا Frontend پیاده‌سازی نشده است. بنابراین خاموش‌بودن Login در حال حاضر صرفاً یک تصمیم آینده است، نه وضعیت اجرایی.
- OTP جدید در D1 نگهداری و مصرف/افزایش تلاش‌های ناموفق آن با UPDATE شرطی انجام می‌شود. مسیر سازگاری OTP قدیمی KV هنوز وجود دارد و به دلیل نبود compare-and-swap در KV، در برابر درخواست‌های هم‌زمان تضمین اتمیک ندارد.
- Sessionها در KV ذخیره می‌شوند؛ توکن خام در KV ذخیره نمی‌شود و فقط hash توکن به‌عنوان کلید استفاده می‌شود. Frontend توکن را فقط در حافظه نگه می‌دارد؛ refresh مرورگر نشست قابل استفاده در UI را از بین می‌برد، حتی اگر رکورد Session در KV هنوز معتبر باشد.
- نقش‌های معتبر در کد `owner`، `manager` و `employee` هستند. ماتریس مجوزها در `worker/src/auth/permissions.js` تعریف شده و نباید با خاموش‌کردن Login تغییر یا حذف شود.

## ماتریس مجوز فعلی

- `owner`: تمام منابع خواندنی و نوشتنی، از جمله فهرست کاربران.
- `manager`: خواندن داشبورد، کالا، قیمت، موجودی، فروش، بدهی، مشتری، حضور و غیاب، گزارش و فضای مدیریت انبار؛ نوشتن کالا، مشتری، فروش، حضور و غیاب و داده‌های پایه فضای انبار. فهرست کاربران برای manager مجاز نیست.
- `employee`: خواندن کالا و موجودی و سوابق حضور خودش؛ ثبت فروش با قیمت پایه و ثبت ورود/خروج خودش. داشبورد، گزارش، فروش‌های ثبت‌شده، بدهی، مشتریان، قیمت‌های مدیریتی و مدیریت کالا برای او مجاز نیستند.

این ماتریس از کد Worker استخراج شده است؛ در صورت تفاوت اسناد قدیمی با این بخش، کد فعلی مرجع رفتار اجرایی است.

## سیاست طراحی مصوب برای حالت Login خاموش

تصمیم محصول: در آینده با `AUTH_ENABLED=false`، کاربر برای ورود به برنامه به OTP، رمز، Token یا Session نیاز نداشته باشد؛ اما کد و زیرساخت OTP، Session، مسیرهای auth و اعتبارسنجی نقش‌ها حذف نشوند.

الزامات پیاده‌سازی که هنوز انجام نشده‌اند:

1. یک تنظیم مرکزی در Worker تعیین‌کننده حالت باشد؛ نبود یا مقدار نامعتبر تنظیم باید به حالت امنِ احراز هویت فعال برگردد. خاموش‌کردن فقط با مقدار صریح `false` انجام شود.
2. Frontend وضعیت عمومی auth mode را از Worker دریافت کند و صفحه Login را فقط بر اساس همان وضعیت نمایش دهد؛ Frontend به‌تنهایی مرجع امنیت نباشد.
3. Backend در حالت خاموش نبودن Bearer token یا Session را به‌تنهایی دلیل 401 نداند و یک principal سیستمی صریح و غیرشخصی بسازد.
4. ماتریس سه نقش موجود دست‌نخورده بماند. principal سیستمی باید سیاست جداگانه و صریح داشته باشد؛ نباید به‌جای کارمند، مدیر یا مالک واقعی جا زده شود.
5. عملیات نیازمند هویت واقعی کارمند، به‌ویژه ثبت ورود/خروج و نمایش «حضور خودم»، نباید به نام یک شخص فرضی ثبت شوند. این مسیرها تا تعیین سازوکار معتبر شناسایی فرد، باید محدودیت صریح داشته باشند.
6. دو جدول Audit فعلی، `product_audit_log` و `inventory_workspace_audit`، ستون actor غیرقابل‌تهی و FK به `users` دارند. ثبت عملیات عمومی با actor ساختگی ممنوع است. پیش از فعال‌سازی حالت عمومی باید راهکار نسخه‌دار و بدون از دست‌رفتن رکوردهای Audit طراحی و در D1 آزمایشی تست شود؛ هیچ Migrationای روی Production بدون تأیید اجرا نشود.
7. در حالت فعال‌سازی مجدد، با تغییر تنظیم به `AUTH_ENABLED=true` یا حذف مقدار خاموش، Frontend دوباره Login را نشان دهد و Backend مجدداً Session/OTP و ماتریس نقش‌ها را الزام کند. داده‌های OTP و Session نباید هنگام خاموش‌بودن پاک شوند.

### پیامد امنیتی حالت عمومی

خاموش‌کردن احراز هویت به معنی عمومی‌شدن داده‌های سامانه برای هر دارنده لینک است، نه صرفاً حذف صفحه Login. با توجه به endpointهای موجود، اطلاعات فروش، قیمت خرید، موجودی، بدهی، مشتریان و سوابق حضور ممکن است برای بازدیدکنندگان قابل مشاهده یا تغییر شوند. CORS یا مخفی‌بودن URL جایگزین احراز هویت نیستند. پیش از فعال‌سازی واقعی باید محدوده داده‌ها و عملیات عمومی به‌صورت صریح تأیید شود.

## محدودیت‌های عملیاتی فعلی

- هیچ دسترسی مستقیم مرورگر به D1 وجود ندارد؛ تمام درخواست‌ها از Worker عبور می‌کنند.
- فروش یک‌قلمی است. Triggerهای D1 پس از درج فروش، موجودی را کاهش و بدهی احتمالی را ایجاد می‌کنند؛ API نباید این رفتار را تکرار کند.
- سوابق فروش immutable هستند.
- `POST /api/v1/inventory/adjust` و `POST /api/v1/debts/:saleId/settle` تا ایجاد ledger قابل حسابرسی، با `501 LEDGER_REQUIRED` غیرفعال‌اند.
- Migrationهای `0001`، `0002` و `0003` در مخزن موجودند و Worker به آن‌ها وابسته است؛ اجرای آن‌ها روی D1 میزبانی‌شده در این ممیزی تأیید نشده است.
- وضعیت Schema، Triggerها و Migration history دیتابیس Production هنوز با دسترسی read-only تأیید نشده است.
- GitHub Actions مخزن Frontend را روی GitHub Pages منتشر می‌کند؛ Worker جداگانه مستقر می‌شود.
